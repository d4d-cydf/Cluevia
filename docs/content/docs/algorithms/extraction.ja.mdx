---
title: "資料の構造化"
description: "分析範囲を確定し、オントロジーに合わせて表と文書を処理した後、根拠のある結果のみを保存する過程。"
---

資料の構造化は、**分析意図 → オントロジー → 資料ごとの処理 → 根拠の検証 → 保存**の順に進む。入力全体を一度にグラフへ変換する単一の呼び出しではなく、完了した区間を保存し、続きから再開できるサーバータスクである。

| 入力 | 出力 | 主な実装 |
| --- | --- | --- |
| 質問、原文資料、オプション `analysisBrief` | オントロジー定義、分析記録、部分グラフと統合ケース | `ontology-planner.ts`, `analysis-pipeline.ts`, `analysis-case.ts` |

## 1。分析の意図と根拠を区別する [#1-분석-의도와-근거를-구분한다]

確認段階では、最大 10 件の資料について合計 12,000 文字以下のプレビューを使用する。依頼が曖昧な場合は 1–3 個の質問を提示し、最大二回確認する。利用者が最終的な範囲を確認した後、原本のアップロードとタスク登録を行う。

`analysisBrief`は分析目的・範囲・希望する結果を盛り込みます。ユーザー意図であり、原文の事実に代わる出典として使用しません。質問だけがあり、資料がない場合は、オントロジーのみを設計します。

ファイルや日付の範囲が明示されていれば、`analysis-scope.ts` が適用する。日付比較の対象は指定された構造化列の有効な ISO 日付であり、日付が不明な記録や、否認・訂正・反証の手掛かりがある記録は引き続き検討する。除外した資料も原文と分析記録として保存する。

## 2。資料全体を見てオントロジーを決める [#2-자료-전체를-살펴보고-온톨로지를-정한다]

サーバーは全文を走査し、列、観測型、長さの統計と例を作成する。一般文書では、全区間から決定的な reservoir 標本を選ぶ。短い文書で先頭区間・標本・末尾区間の内容が重なる場合は、設計入力から重複を除く。標本化は設計入力を減らすための手段であり、すべての希少型を含む保証はない。原文と全行は保存し、後続の抽出に使用する。

オントロジー デザインのデフォルトのエフォートは `medium` です。データ型に合わせた簡潔なプロンプトと応答コントラクトを使用して、オブジェクト タイプ、プロパティ、主キー、関係タイプ、およびデータ マッピングを要求します。サーバーは共通フィールドに値を入力し、定義とマッピングを検証して、それらを抽出スキーマとして使用します。ユーザーが互換性のある既存の オントロジー を選択した場合、設計呼び出しを省略できます。

設計タイムアウトには例を省略して一度再試行します。検証補完も最大1回なので、スキーマ設計呼び出しは合計3回以内です。キャンセル・認証・呼出限度エラーにはタイムアウト再試行を適用しません。

## 3。資料の性格に応じて処理する [#3-자료의-성격에-따라-처리한다]

| 素材 | 処理方法 |
| --- | --- |
| 検証済み列マッピングを持つ表 | サーバーが各行をタイプ・属性・関係に変換 |
| 表の説明列・本文列 | 別途意味解析を行い、既にマッピングしたオブジェクトの根拠も渡す |
| 一般文書 | 原文を区間に分けて固定されたオントロジーに合わせてCodexで抽出 |
| 限られた選択肢で表現可能な判定 | 設定されている場合はJevを使用し、不確実な結果はCodexレビュー |

サーバーが付与する `evidenceId` は原文の記録を区別するためのものである。資料に存在しない業務上の識別キーをモデルに生成させるためには使用しない。短い独立記録をまとめて分析する場合も、資料ごとの検討結果を要求する。

Jev判定は、分類とレビューを支援する候補です。分類結果だけでは関係の存在や同一オブジェクトであることを確定しません。否認・訂正・再引用手がかりと複雑な文脈は原文レビュー経路に伝えます。

## 4。原文と契約で結果を検証する [#4-원문과-계약으로-결과를-검증한다]

`parseExtraction` は、オントロジーの型・属性・関係の制約を検査する。引用した資料 ID が実際の入力に存在し、引用文が対応する原文に正確に含まれている必要がある。識別子と根拠に基づく主キーにも原文確認の規則を適用する。

検証エラーは、制限された補完要求でモデルに渡されます。タイムアウト区間は小さく分割して再試行できます。完了した区間のグラフ・原文・チェックポイントは一緒に保存して作業再開時の重複生成を避けます。

原文に引用文が存在するという事実だけで、解釈の正確さまで証明するものではありません。検証の2つの層は[データ検証](/ja/docs/algorithms/validation)から区別されます。

## 5。記録を1つのケースにリンクする [#5-기록을-하나의-케이스로-연결한다]

`analysis-case.ts`は、同じジョブの保存された履歴を集めます。保存されたオブジェクト ID と オントロジー 範囲・タイプを基準に連結し、表示名が同じという理由だけで新たにマージしません。

関係と出来事は記録別の根拠を維持します。同じオブジェクトのプロパティが異なる場合、競合を表示し、各履歴の値を残します。統合自体は、新しいモデル呼び出しなしで保存結果として計算されます。

## キャッシュとコスト [#캐시와-비용]

オントロジー設計キャッシュは、検証済みの定義を SQLite に既定で最大 50 件保存し、サーバー再起動後も利用できる。キーには全文の SHA-256、資料メタデータ、質問、確定範囲、モデルと effort、設計設定、契約バージョンを含む。全資料の走査とプロファイル作成後に検索するため、キャッシュが省略する処理は設計モデルの呼び出しと Jev ルール設計である。読み出した定義は再検証し、新しいタスクのオントロジー ID・バージョンを適用して、ケース間のオブジェクト識別範囲を分離する。抽出エラーに伴うスキーマ修正ではキャッシュを使わず、破損または読み出し不能なキャッシュも新規設計で処理する。Jev ルール設計に失敗した結果や、原文列のマッピングが不完全な結果は保存せず、次回再設計できるようにする。

抽出キャッシュは資料だけでなく、オントロジー、処理バージョン、モデル・effort、確定範囲と判定設定などをキーに含みます。最近7日以内に結果を再利用し、資料を再アップロードすると、出典IDを現在の入力に合わせて再接続して検証します。進行中の冗長要求は同じ実行範囲内で合計されます。

処理履歴は全体オントロジー設計時間と資料プロファイル・モデル応答・スキーマ検証・Jevルール時間を分けて記録し、設計キャッシュ再使用回数を表示します。詳細時間は全体の設計時間を上書きしません。計測を追加する前の実行には対応する詳細値はありません。

実際の 188 文字の入力、質問、確定範囲を維持した一回の設計では、`medium` と簡潔な応答契約・プロンプトを適用した処理時間は 84.1 秒であり、過去の `high` 実行の 121.9 秒より約 31% 短かった。同じ入力のキャッシュ再実行は、モデル呼び出しなしで 1.668 ms で完了した。これは単一の設計とキャッシュ検索の観測値であり、提供者や実行環境の負荷を統制した品質・性能比較ではない。グラフ分析全体や別の初回設計の所要時間を保証するものではない。[測定範囲と結果](https://github.com/d4d-cydf/Cluevia/blob/main/docs/evaluations/ontology-design-medium-cache.json)。

表変換はレコードとマッピング数の影響を受け、文書処理コストは区間数・モデル呼び出し・再試行によって異なります。すべての区間を処理しても、すべての事実の抽出や遠隔区間間の関係の発見を保証するわけではありません。
