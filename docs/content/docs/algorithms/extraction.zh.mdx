---
title: "资料结构化"
description: "确定分析范围，按本体处理表格和文档，并仅保存具有原文依据的结果。"
---

资料结构化依次经过**分析意图 → 本体 → 按资料处理 → 证据验证 → 存储**。它不是将全部输入一次性转换为图的单次调用，而是可保存已完成区段并继续执行的服务器任务。

| 输入 | 输出 | 主要实施 |
| --- | --- | --- |
| 问题、原始资料、可选的 `analysisBrief` | 本体定义、分析记录、子图及整合后的案例 | `ontology-planner.ts`, `analysis-pipeline.ts`, `analysis-case.ts` |

## 1. 区分分析意图与事实依据 [#1-분석-의도와-근거를-구분한다]

澄清阶段使用最多 10 份资料的预览，总长度不超过 12,000 字符。请求含糊时提出 1–3 个问题，最多进行两轮澄清。用户确认最终范围后，才上传原始资料并登记任务。

`analysisBrief` 记录分析目的、范围与预期结果。它表达用户意图，不能替代原文作为事实来源。只有问题而没有资料时，仅设计本体。

若指定了文件或日期范围，由 `analysis-scope.ts` 应用相应约束。日期比较针对指定结构化列中的实际 ISO 日期；日期不明或含有否认、更正、反证线索的记录仍须审查。被排除的资料也作为原文和分析记录保留。

## 2. 考察全部资料并确定本体 [#2-자료-전체를-살펴보고-온톨로지를-정한다]

服务器扫描全文，生成列结构、观测类型、长度统计和示例；对于普通文档，则从全部区段中选取确定性的 reservoir 样本。短文档的首段、样本和末段若内容相同，会在设计输入中去重。采样旨在缩减设计输入，并不保证覆盖所有稀有类型。原文和全部行仍予保留，供后续抽取使用。

本体设计的默认 effort 为 `medium`。系统通过简洁提示及适配资料形式的响应契约，请求对象类型、属性、主键、关系类型与资料映射。服务器补充公共字段，验证定义与映射后，将其用作抽取模式。若用户选择兼容的现有本体，可跳过设计调用。

设计超时时，缩减示例后重试一次；验证修正也最多进行一次，因此模式设计调用总数不超过 3 次。取消、身份验证失败或调用额度错误不适用超时重试。

## 3. 按资料性质选择处理方式 [#3-자료의-성격에-따라-처리한다]

| 材料 | 处理方法 |
| --- | --- |
| 有验证的列映射表 | 服务器将每个行转换为类型，属性或关系。 |
| 表格中的说明列或正文列 | 单独进行语义分析，并传入已映射对象的依据 |
| 普通文档 | 将原文划分为区段，由 Codex 按固定本体抽取 |
| 可用有限选项表示的判定 | 启用时使用 Jev；不确定结果交由 Codex 审查 |

服务器分配的 `evidenceId` 用于区分原文记录，不能用来让模型编造资料中不存在的业务标识键。即使合并处理若干简短的独立记录，也须分别返回各份资料的审查结果。

Jev 判定是辅助分类和审查的候选结果，不能单凭分类结果确认关系存在或对象相同。含有否认、更正、转引线索或复杂语境的内容，应转交原文审查流程。

## 4. 按原文与数据契约验证结果 [#4-원문과-계약으로-결과를-검증한다]

`parseExtraction` 检查本体的类型、属性和关系约束。引用的资料 ID 必须存在于实际输入中，引文必须与对应原文精确匹配。标识符和基于证据的主键也须接受原文核查。

验证错误通过次数受限的修正请求传回模型。超时区段可进一步拆分后重试。已完成区段的图、原文与检查点一并保存，以避免恢复任务时重复生成。

引文存在于原文，并不意味着对它的解释必然正确。两层验证的区别见[数据验证](/zh/docs/algorithms/validation)。

## 5. 将记录整合为一个案例 [#5-기록을-하나의-케이스로-연결한다]

`analysis-case.ts` 汇总同一任务的已保存记录，依据对象 ID、本体范围和类型建立关联；不会仅因显示名称相同而再次合并对象。

关系和事件保留各记录的依据。同一对象的属性值不一致时，系统标记冲突并保留每条记录的值。整合直接根据已存储结果计算，无须再次调用模型。

## 缓存与成本 [#캐시와-비용]

本体设计缓存默认在 SQLite 中保留最多 50 份已验证定义，服务器重启后仍可使用。缓存键包含全文 SHA-256、资料元数据、问题、确认范围、模型与 effort、设计配置及契约版本。缓存查询发生在扫描全部资料并建立概况之后，因此命中缓存所省略的是设计模型调用和 Jev 规则设计。读取的定义须重新验证，并应用新任务的本体 ID 与版本，以隔离不同案例的对象识别范围。因抽取错误而进行的模式修正会绕过缓存；损坏或无法读取的缓存触发重新设计。Jev 规则设计失败或原文列映射不完整的结果不写入缓存，以便下次重新设计。

抽取缓存的键不仅包含资料，还包含本体、处理版本、模型与 effort、确认范围和判定配置等。系统复用最近 7 天内的结果；资料重新上传时，将来源 ID 重新关联到当前输入并验证。同一执行范围内正在进行的重复请求会合并。

处理日志分别记录本体设计总耗时及资料概况、模型响应、模式验证、Jev 规则的耗时，并显示设计缓存复用次数。分项耗时不替代总耗时；添加计时功能之前的运行没有这些分项数据。

在一次保持实际 188 字符输入、问题与确认范围不变的设计中，采用 `medium` 及简洁响应契约与提示后耗时 84.1 秒，比此前 `high` 运行的 121.9 秒缩短约 31%。相同输入命中缓存后，无须调用模型，在 1.668 ms 内完成。这只是单次设计与缓存查询的观测，未控制提供方及执行环境负载差异，不能视为严格的质量或性能对照，也不保证完整分析或其他首次设计的耗时。[测量范围与结果](https://github.com/d4d-cydf/Cluevia/blob/main/docs/evaluations/ontology-design-medium-cache.json)。

表格转换成本取决于记录数和映射数；文档处理成本则取决于区段数、模型调用和重试。处理完全部区段，并不保证抽取出所有事实或发现相距较远区段之间的关系。
