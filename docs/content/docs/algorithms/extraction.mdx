자료 구조화는 **분석 의도 → 온톨로지 → 자료별 처리 → 근거 검증 → 저장**으로 나뉩니다. 전체 입력을 한 번에 그래프로 바꾸는 단일 호출이 아니라, 완료한 구간을 보존하고 이어서 실행할 수 있는 서버 작업입니다.

| 입력 | 출력 | 주요 구현 |
| --- | --- | --- |
| 질문, 원문 자료, 선택적 `analysisBrief` | 온톨로지 정의, 분석 기록, 부분 그래프와 통합 케이스 | `ontology-planner.ts`, `analysis-pipeline.ts`, `analysis-case.ts` |

## 1. 분석 의도와 근거를 구분한다

확인 단계는 최대 10개 자료의 미리보기 총 12,000자 이하를 사용합니다. 요청이 모호하면 1–3개 질문을 제시하며 최대 두 차례 확인합니다. 사용자가 최종 범위를 확인한 뒤 원본 업로드와 작업 등록을 진행합니다.

`analysisBrief`는 분석 목적·범위·원하는 결과를 담습니다. 사용자 의도이며 원문의 사실을 대신하는 출처로 사용하지 않습니다. 질문만 있고 자료가 없으면 온톨로지만 설계합니다.

명시적인 파일·날짜 범위가 있으면 `analysis-scope.ts`가 적용합니다. 날짜 비교는 지정한 구조화 열의 실제 ISO 날짜에 적용하며, 날짜가 불명확하거나 부인·정정·반증 단서가 있는 기록은 계속 검토합니다. 제외한 자료도 원문과 분석 기록으로 보존합니다.

## 2. 자료 전체를 살펴보고 온톨로지를 정한다

서버는 전체 원문을 스캔해 자료의 열·관측 타입·길이 통계와 예시를 만들고, 일반 문서는 전체 구간에서 결정적인 reservoir 표본을 선택합니다. 짧은 문서의 첫 구간·표본·마지막 구간이 같은 내용이면 설계 입력에서 중복을 제거합니다. 표본은 설계 입력을 줄이는 수단이며, 모든 희귀 유형을 포함한다는 보장은 없습니다. 원문과 전체 행은 보관하여 이후 추출에 사용합니다.

온톨로지 설계의 기본 effort는 `medium`입니다. 간결한 프롬프트와 자료 형태에 맞춘 응답 계약으로 객체 유형, 속성, 기본 키, 관계 유형과 자료 매핑을 요청합니다. 서버가 공통 필드를 채우고 정의와 매핑을 검증한 뒤 추출 스키마로 사용합니다. 사용자가 호환되는 기존 온톨로지를 선택하면 설계 호출을 생략할 수 있습니다.

설계 시간 초과에는 예시를 축약해 한 번 재시도합니다. 검증 보완도 최대 한 번이므로 스키마 설계 호출은 총 3회 이내입니다. 취소·인증·호출 한도 오류에는 시간 초과 재시도를 적용하지 않습니다.

## 3. 자료의 성격에 따라 처리한다

| 자료 | 처리 방식 |
| --- | --- |
| 검증된 컬럼 매핑이 있는 표 | 서버가 각 행을 유형·속성·관계로 변환 |
| 표의 설명·본문 열 | 별도 의미 분석; 이미 매핑한 객체의 근거를 함께 전달 |
| 일반 문서 | 원문을 구간으로 나누어 고정된 온톨로지에 맞춰 Codex로 추출 |
| 제한된 선택지로 표현 가능한 판정 | 설정된 경우 Jev를 사용하고 불확실한 결과는 Codex 검토 |

서버가 부여하는 `evidenceId`는 원문 기록을 구분합니다. 자료에 없는 업무 식별 키를 모델이 만들어 채우는 용도로 쓰지 않습니다. 짧은 독립 기록을 묶어 분석할 때도 자료별 검토 결과를 요구합니다.

Jev 판정은 분류와 검토를 돕는 후보입니다. 분류 결과만으로 관계의 존재나 동일 객체임을 확정하지 않습니다. 부인·정정·재인용 단서와 복잡한 문맥은 원문 검토 경로로 전달합니다.

## 4. 원문과 계약으로 결과를 검증한다

`parseExtraction`은 온톨로지의 유형·속성·관계 제약을 검사합니다. 인용한 자료 ID가 실제 입력에 있어야 하고, 인용문은 해당 원문에 정확히 존재해야 합니다. 식별자와 근거 기반 기본 키에도 원문 확인 규칙을 적용합니다.

검증 오류는 제한된 보완 요청으로 모델에 전달합니다. 시간 초과 구간은 더 작게 나누어 재시도할 수 있습니다. 완료한 구간의 그래프·원문·체크포인트는 함께 저장하여 작업 재개 시 중복 생성을 피합니다.

원문에 인용문이 존재한다는 사실만으로 해석의 정확성까지 증명하지는 않습니다. 검증의 두 계층은 [데이터 검증](/docs/algorithms/validation)에서 구분합니다.

## 5. 기록을 하나의 케이스로 연결한다

`analysis-case.ts`는 같은 작업의 저장된 기록을 모읍니다. 저장된 객체 ID와 온톨로지 범위·유형을 기준으로 연결하며, 표시 이름이 같다는 이유만으로 새로 병합하지 않습니다.

관계와 사건은 기록별 근거를 유지합니다. 같은 객체의 속성이 서로 다르면 충돌을 표시하고 각 기록의 값을 남깁니다. 통합 자체는 새 모델 호출 없이 저장 결과로 계산합니다.

## 캐시와 비용

온톨로지 설계 캐시는 검증된 정의를 SQLite에 기본 최대 50개 보관하며, 서버 재시작 뒤에도 사용할 수 있습니다. 전체 원문의 SHA-256·자료 메타데이터·질문·확정 범위·모델과 effort·설계 설정·계약 버전을 키에 포함합니다. 전체 자료 스캔과 프로필 작성 후 조회하므로 캐시가 생략하는 작업은 설계 모델 호출과 Jev 규칙 설계입니다. 읽은 정의는 재검증하고 새 작업의 온톨로지 ID·버전을 적용하여 케이스 간 객체 식별 범위를 분리합니다. 추출 오류에 따른 스키마 보완은 캐시를 건너뛰고, 손상되거나 읽을 수 없는 캐시는 새 설계로 처리합니다. Jev 규칙 설계 실패나 불완전한 원문 열 매핑이 남은 결과는 캐시에 저장하지 않아 다음 실행에서 재설계할 수 있습니다.

추출 캐시는 자료뿐 아니라 온톨로지, 처리 버전, 모델·effort, 확정 범위와 판정 설정 등을 키에 포함합니다. 최근 7일 이내 결과를 재사용하며, 자료를 다시 업로드하면 출처 ID를 현재 입력에 맞게 다시 연결하고 검증합니다. 진행 중 중복 요청은 같은 실행 범위 안에서 합칩니다.

처리 내역은 전체 온톨로지 설계 시간과 자료 프로필·모델 응답·스키마 검증·Jev 규칙 시간을 나누어 기록하고, 설계 캐시 재사용 횟수를 표시합니다. 세부 시간은 전체 설계 시간을 대체하지 않으며, 계측을 추가하기 전 실행에는 해당 세부 값이 없습니다.

실제 188자 입력·질문·확정 범위를 유지한 설계 1회에서 `medium`과 간결한 응답 계약·프롬프트를 적용한 시간은 84.1초로, 과거 `high` 실행의 121.9초보다 약 31% 짧았습니다. 동일 입력의 캐시 재실행은 1.668ms에 모델 호출 없이 끝났습니다. 이는 단일 설계와 캐시 조회의 관측값이며 제공자·실행 환경 부하 차이를 통제한 품질·성능 비교가 아닙니다. 전체 그래프 분석 시간이나 다른 최초 설계의 시간을 보장하지 않습니다. [측정 범위와 결과](https://github.com/d4d-cydf/Cluevia/blob/main/docs/evaluations/ontology-design-medium-cache.json).

표 변환은 레코드와 매핑 수에 영향을 받고, 문서 처리 비용은 구간 수·모델 호출·재시도에 따라 달라집니다. 모든 구간을 처리해도 모든 사실의 추출이나 먼 구간 사이 관계의 발견을 보장하지는 않습니다.
