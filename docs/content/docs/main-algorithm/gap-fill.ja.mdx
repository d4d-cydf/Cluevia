根拠の欠落の診断 が役立つためには、その結果がその後の調査で確認できる特定の条件につながる必要があります。 Gap Fill は、データ型、必須フィールド、イベント範囲、および受け入れ基準の観点からこれらの条件を表します。 補完 行動はまだ満たされていないニーズへの応答であり、行動の実行自体は十分な証拠を保証するものではありません。取得されたデータと変更された決定は、新しい snapshot で再評価されます。

## 共通アクション契約 [#공통-액션-계약]

```ts
type FillAction = {
  id: string;
  runId: string;
  gapIds: string[];
  targetClaimId: string;
  requirementIds: string[];
  actionType: 'SEARCH_EVIDENCE' | 'REQUEST_EVIDENCE' | 'EXPLAIN_MISMATCH'
    | 'EXPLAIN_TRUST' | 'TRACE_SOURCE' | 'REQUEST_SOURCE' | 'PROPOSE_CHAINS';
  reason: string;
  requiredEvidence: { kinds: string[]; fields: string[]; eventScopeId: string };
  acceptanceCriteria: string[];
  status: 'PROPOSED' | 'RUNNING' | 'WAITING_USER' | 'COMPLETED' | 'FAILED';
  resultEvidenceIds: string[];
  nextEvaluationStages: string[];
};
```

LLMは検索式・説明・戦略を作成し、ツールは実際の検索・原文確保を行い、コードは返却資料・予算・状態を検証する。 LLMが知っていると述べた文書を実際に確保した資料として記録しない。

## EVIDENCE_MISSING・直接資料検索、必要に応じてユーザーリクエスト [#evidence_missing--직접-자료-검색-필요-시-사용자-요청]

**入力:** 空いているrequirement、目標主張、対象・事件条件と許容資料形態。

1. requirementが満たされるためには、どのフィールドが必要かを指定します。
2. 識別子・期間・場所・資料の種類を含む検索式を作る。
3. インターネットから直接関連する原文を検索し、実際のURLと本文を確保する。支持・反証 結果を全て保存する。
4. タイトル・検索 snippetだけ合う結果を証拠leafとして採用しない。原文区間、対象と事件を対照する。
5. 公開資料で確保できない場合は、探索範囲とその判断根拠を記録し、ユーザーに必要な資料を要請する。

「検索結果なし」は「その資料が世界にない」を意味しない。インターネット確保不可の理由は、`NOT_FOUND_WITHIN_BUDGET`、`PRIVATE_RECORD_REQUIRED`、`ACCESS_UNAVAILABLE`のように区分する。検索予算を使い果たした場合、その範囲内で見つからなかったと説明する。

**リクエスト例：**「O-17と倉庫入庫番号を関連付けるデータはありません。注文番号と入庫番号が一緒に表示されている元の受領証または注文–入荷照合が必要です。」

**完了条件:** 資料が確保され、1-3の空き要求を満たす候補が生まれる。 根拠の欠落解消は以後1-4・1-5・1-7・1-8再評価で決定する。

## EVIDENCE_INSUFFICIENT · 不足している支持内容の説明 [#evidence_insufficient--부족한-지지-내용-설명]

**入力:** 不適格 binding、判定 enum、原文区間と aceptance criteria。

説明は「信頼できない」という一般フレーズの代わりに、**資料が実際に言うこと→目標が要求するもの→その違い→追加で必要な資料**の順に作成する。

**例：**「現在のメールは10月5日配送予定としか書かれていません。目標は実際の配達完了ですのでこのメールだけでは十分ではありません。配達時刻・受領対象・注文番号を確認できる受領証または入庫記録が必要です。」

反証なら原文にどんな反対主張があるかを一緒に見せる。 `UNREVIEWED`やモデルエラーなら不足した根拠で判定完了したとは言わず検討を先に完了する。事件メタデータUNKNOWNも抜けたフィールドを具体的に要請する。

**完了条件：**新資料または見直しで該当binding・代替bindingが`SUPPORTED`になり、必要な再検査を通過する。

## EVENT_MISMATCH ・接続不可説明 [#event_mismatch--연결-불가-설명]

**入力：**失敗したイベントルールID、期待メタデータ、および観測メタデータ。

| 表示するもの | 例 |
| --- | --- |
| 接続しようとしていた主張 | O-17 インド完了 |
| 適用ルール | 注文番号同じ+指定倉庫+配達期間 |
| 衝突項目 | 目標O-17、資料O-71 |
| 対応する原文位置 | 受領証注文番号フィールド |
| 結論 | この受領証をO-17の完了根拠に接続できない |

ユーザーに接続不可を通知し、その資料を現在の候補から除外する。対象に合った他の資料があれば新しい候補と評価することができるが、既存資料の番号・日付を目標に合わせて修正しない。

単純メタデータの欠落は、このアクションではなく不十分なデータ要求として送信されます。解析エラーが確認され訂正された場合でも、オリジナルは保存し、新しいメタデータバージョンで1-5を再実行する。

**完了条件：**現在の接続が成立しないという診断を正確に伝えた状態。アクションの完了は、目標主張の立証や gap の解消を意味しない。

## TRUST_WEAK・ミニグラフとボトルネックの説明 [#trust_weak--미니-그래프와-병목-설명]

**入力：** 信頼度計算トレース、しきい値、共有出典・依存性、不十分なノード。

ミニグラフは、少なくともルートまでの経路、ボトルネック主張、使用した証拠、関係演算子、ノード別スコア・未知状態を含む。 ANDの他の前提条件を隠すのではなく、折りたたまれた要約ノードとして残します。

```text
인도 완료 H [AND, 0.72 / 예제 기준 0.80]
├─ 인도 기록 C1 [0.90]
│  └─ 창고 원본 로그 E1
└─ 주문 연결 C2 [0.80] ← 이 연결의 근거를 강화해야 함
   └─ 주문–입고 연결표 E3
```

**説明例：**「引き渡し記録と注文への対応付けの両条件が必要です。現在のスコアモデルでは 0.90×0.80=0.72 となります。同じログを転載した記事を追加しても、独立した根拠にはならず、支持は増えません。注文と入庫記録の接続を確認できる原本の番号対照表が必要です。」

<ResearchDiagram kind="bottleneck" number="G2" />

図G2は、[完全な実行例](/ja/docs/main-algorithm/worked-example)の実行Cを示しています。同じANDモデルで1つのサブスコアだけが変化すると仮定すると、次の感度が得られます。

<Equation number="G1" label={"固定されたANDモデルの局所感度"} tex={String.raw`\begin{aligned}s(H)&=s(C_1)s(C_2)\\\frac{\partial s(H)}{\partial s(C_1)}&=s(C_2),\qquad\frac{\partial s(H)}{\partial s(C_2)}=s(C_1)\end{aligned}`} />

これは式の変化率であり、実際 補完 アクションの効果予測値ではない。新しいデータが他の観測に依存したり論理構造を変更したりすると、同じ計算を再利用することはできません。

可能であれば、候補アクションを「どの requirement の、どの不確実性を減らすか」で比較する。対応するモデルがない状態で予想スコア上昇を確定値として表示しない。独立性が不明なため区間が広い場合は、資料数を増やすより観測経路の確認を優先する。

**完了条件:** 新しい根拠・系譜・依存性確認を再評価した結果、しきい値の充足が確認される。しきい値を下げる変更は、資料補完と区別して別のポリシーバージョンで記録する。

## PROVENANCE_UNKNOWN・円出典表記または検索 [#provenance_unknown--원출처-표기-또는-찾기]

**入力:** D/Eデータ、確認された系譜、追跡終了理由。

原文発行機関・作成者・初公開アドレス・発行日・引用ページ・記録識別子のうち抜けた項目を説明する。引用URLがあれば1-7の限度内で円出典を探し、オンラインで確認できなければユーザーが知っている円出典表記を要請する。

**例：**「添付画像に元のレポート名と発行機関がありません。レポートの元のURL、発行機関、そのページ、または元のファイルを教えてください。」

URLを記入したという事実だけで評価を上げない。実際の原文と資料が同じ内容であることを確認し、再引用経路を検証する。元出典を見つけたとしても主張支持判定と事件一致は別途だ。

**完了条件：**系譜検証と出典再評価の結果、D / E問題を解消し、関連候補を再検査する。

## CHAIN_UNKNOWN・チェーン完成戦略3個 [#chain_unknown--체인-완성-전략-3개]

**入力:** ルートまで完成したチェーンが0個で評価が完了した結果、原因gapリスト、元の論理式。

最終目標と必須条件を維持しながら、異なる資料確保戦略を**3つ**提示する。まだない資料や連結は計画で表示し、実際に発見された事実のように描かない。

| 戦略例 | 最初に見つける材料の種類 | 期待される接続 | 適切な状況 |
| --- | --- | --- | --- |
| 1。直接オリジナル履歴 | 署名 受領証・原本取引記録・業務システム院長 | 事件結果と対象識別子を１つの資料で確認 | オリジナルにアクセス可能な場合 |
| 2。時系列交差検証 | 出荷・入庫・受領ログと識別子対照表 | ターゲットキーを保持し、イベントの前後を接続 | 一つの総合資料がない場合 |
| 3。独立観測の組み合わせ | 相手機関記録・直接観測資料・別途保管証明 | 同じ対象・事件の独立資料を連結 | 既存資料が再引用した系列に追い込まれた場合 |

策略を進めていくのです `requiredEvidence` ,  `closedGapIds` ,  `remainingGaps` ,  `eventJoinRules` ,  `sourceIndependenceNeeds` ,  `availability` すべてのケースに3つの実行可能な経路があることを保証することはできません.実行できない戦略はなぜ不可能であり,必要なアクセス条件を示すが,偽りの出典を作り,数字を記さない.

もともとツリーになかった代替ロジックを提案すると、`proposedTreeRevision`で区切って同じ目標を十分に支持するかを検討した後、新しいツリーバージョンに反映する。既存のAND必須条件をクリアしてチェーンを完成したものにしない。

**完了条件：**3つの戦略とデータニーズをユーザーに提供します。実際のギャップ解消は、戦略の実行後に新しい実行で完成チェーンを確認する必要があります。

## 複数の根拠の欠落の優先順位と重複アクション [#여러-공백의-우선순위와-중복-액션]

ROOTを防ぐ詳細根拠の欠落を先に説明し、ORの選択されていない代替根拠の欠落は後に置く。 `CHAIN_UNKNOWN`戦略は詳細な原因を参照してください。同じ原文一つでmissing・provenance問題を一緒に解くことができればアクション一つに複数のgap IDを連結する。

優先順位は、データのアクセシビリティ、満たされる必須要件の数、期待される不確実性の削減、実行コストを理由と一緒に提案します。これを自動的に正確な効用数値と表現しない。

## 繰り返しと終了 [#반복과-종료]

```text
액션 실행 → 후보 자료 등록 → 새 snapshot
  → Gap Find 재실행 → 이전 gap과 비교
```

新しい入力 hash・判定・系譜が変わらなければ同じ要求を繰り返さない。ユーザー資料が必要な場合は`WAITING_USER`、予算に達した場合は`PAUSED_BY_BUDGET`、ニーズを満たす場合は`RESOLVED`のように補完ループ状態を別々に管理します。これは6つのGapTypeを増やすことではありません。

Gap Fillは`maxRounds`、検索URL・時間・呼出予算で有限に実行する。確保不可を立証失敗と区別し、追加資料なしで根拠の欠落が解消されたと自動終了しない。
