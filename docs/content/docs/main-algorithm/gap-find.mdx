Gap Find의 목적은 현재 자료로 구성할 수 있는 입증 경로를 평가하고, 각 경로가 유지되거나 제외되는 이유를 설명하는 데 있다. 이때 제외되는 것은 특정 주장에 대한 후보 조합이며 원본 자료 자체가 아니다. 따라서 한 대안의 실패, 목표 전체의 입증 경로 부재, 평가 미완료를 서로 다른 상태로 보존해야 한다. 아래 절차는 이 원칙을 각 단계의 입력과 판정 규칙으로 구체화한다.

<ResearchDiagram kind="gates" number="F1" />

## 1-1 · 목표와 사건 범위 고정

질문을 검증 가능한 주장으로 바꾸고 대상·행위·시각·장소·조건을 정한다. 사용자가 요구한 결론을 더 약한 결론으로 바꾸지 않는다. “소유했는가”와 “소유했다는 기사가 있는가”는 다른 주장이다.

목표를 검증하려면 필요한 항목과 판정 기준을 `EvidenceNeed`에 적는다. 사건 시각과 자료 발행 시각을 분리하고, 미상 필드는 미상으로 유지한다. 목표나 논리 연결 자체가 모호하면 자료 부족으로 단정하지 말고 논리 설계를 먼저 보완한다.

## 1-2 · Why-not Tree 생성

LLM은 하위 주장·증거 요구·연산자 후보를 제안한다. 코드가 ID·참조·순환·빈 논리 노드와 필수 requirement를 검사한다. 각 내부 연결에는 “이 자식 조건들이 충족되면 왜 이 부모 주장을 지지하는가”를 설명하는 `inferenceRule`이 필요하다.

자료의 수만 보고 연산자를 추정하지 않는다. 증거가 없는 요구도 유지한다. NOT_SUPPORT는 [확정된 부정 입증 규칙](/docs/main-algorithm/model)에 따라 AND로 정규화한다.

## 1-3 · 존재하는 leaf로 집합 트리 생성

자료 본문 또는 검사 가능한 기록 구간이 현재 snapshot에 존재하고 참조가 유효한 leaf만 사용한다. URL만 있고 내용을 확보하지 못했거나, 파일 처리가 끝나지 않았다면 실제 증거가 확보되었다고 보지 않는다.

노드 `v`에 가능한 후보들의 집합을 `F(v)`라 정의한다. 아래의 집합 원소는 자료 ID만이 아니라 requirement에 연결된 binding이다.

<Equation number="F1" label="후보 구성의 기저 조건" tex={String.raw`F(b)=\{\{b\}\},\qquad F(r_{\mathrm{missing}})=\varnothing`} />

<Equation number="F2" label="OR의 합집합과 AND의 조합" tex={String.raw`\begin{aligned}F_{\mathrm{OR}}(v)&=\bigcup_{i=1}^{n}F(c_i)\\F_{\mathrm{AND}}(v)&=\left\{\bigcup_{i=1}^{n}w_i\;\middle|\;w_i\in F(c_i)\right\}\end{aligned}`} />

NOT_SUPPORT의 후보 구성에는 AND와 같은 규칙을 적용한다.

예를 들어 `AND(OR(a,b), c)`의 후보는 `{a,c}`, `{b,c}`다. c가 없으면 후보는 0개다. a 또는 b가 남아 있다고 `AND(a)`로 바꾸지 않는다.

<WitnessExplorer number="F2" />

<Callout title="공집합과 빈 후보의 구분">
`∅`는 가능한 후보가 없다는 뜻이고 `{∅}`는 빈 증거만으로 성립하는 후보 하나라는 뜻이다. 증거가 필요한 주장에 `{∅}`를 만들지 않는다. 빈 AND를 참으로 취급하는 프로그래밍 관례를 증거 판정에 적용하면 안 된다.
</Callout>

루트 후보가 공집합이면 `EVIDENCE_MISSING`과 필수 requirement 경로를 기록하고 해당 실행의 증거 체인 평가는 중단한다. 하위 진단을 별도로 수행할 수 있지만 이후 단계를 통과한 완성 후보로 표시하지 않는다.

가능한 조합이 너무 많으면 지연 생성과 상한을 사용한다. 상한에 도달하면 `INCOMPLETE`이며 “체인 없음”으로 확정하지 않는다. 초기에는 requirement 충족 관계가 다른 후보를 단순 부분집합 비교로 제거하지 않는다.

## 1-4 · 각 자료의 주장 지지 적합성

각 binding마다 해당 부모 주장과 `acceptanceCriteria`를 읽고 자료의 판정 상태를 대입한다. `SUPPORTED`만 통과하고 나머지는 사유와 함께 탈락시킨다. 미검토·모델 오류는 “거짓으로 판정됨”과 구분해 미완료로 기록한다.

| 검사 | 예 |
| --- | --- |
| 대상이 주장과 같은가 | “O-17”의 자료인가, 이름만 비슷한 다른 주문인가 |
| 자료가 말하는 사실의 강도가 충분한가 | 계획·예약과 실제 완료를 구분했는가 |
| 원문 구간이 실제 존재하는가 | 인용이 원문에 있고 잘라낸 문맥이 없는가 |
| 추론 규칙에 필요한 조건이 충족되는가 | 단순 조우를 화물 이전으로 단정하지 않는가 |
| 부정·추정·재인용을 보존했는가 | “아니라고 주장했다”를 실제 부재로 바꾸지 않는가 |

<Equation number="F3" label="적합성 관문 이후에 남는 후보" tex={String.raw`F_{\mathrm{fit}}(v)=\{w\in F(v)\mid\forall b\in w,\;\operatorname{verdict}(b)=\mathrm{SUPPORTED}\}`} />

대상·시간의 구체적인 사건 연결 검사는 1-5에서 별도로 수행한다. 1-4에서 이미 확인한 불충분 사유도 잃지 않는다.

### 부모 연산자에 따른 부적격 판정의 전파

| 부모 | 부적격 자식 처리 |
| --- | --- |
| AND | 해당 자식을 필수로 포함하는 후보 전체 탈락. 필수 조건은 원래 트리에 유지 |
| OR | 해당 대안만 탈락. 다른 대안 검사 계속. 모두 탈락하면 부모도 부적격 |
| NOT_SUPPORT | AND와 동일. 증거 없음이나 부적격을 부정 입증으로 바꾸지 않음 |

부적격마다 `EVIDENCE_INSUFFICIENT`에 판정 값·원문 구간·부족한 요구를 기록한다. 반증은 지지 후보에서 제외한 뒤에도 진단과 사용자 화면에 남긴다.

## 1-5 · 집합 트리 전체의 사건 일치

후보 하나의 자료들이 **같은 사건 또는 명시한 사건 관계**를 구성하는지 검사한다. 이름·단어가 비슷하다는 것만으로 사건을 합치지 않는다.

### 사건 메타데이터 계약

| 필드 | 비교 기준 |
| --- | --- |
| `entityRefs` | 확인된 식별자와 사건 내 역할. 이름만 일치하면 미확인 |
| `eventType` | 행위·관계의 유형. 주문·출하·도착·수령을 구별 |
| `occurredAt` 또는 기간 | 실제 발생 시각과 시간대, 불확실성·정밀도 포함 |
| `locationRefs` | 장소 ID 또는 명시된 포함·이동 관계 |
| `recordKeys` | 주문 번호·거래 번호 등 연결 키 |
| `publishedAt`, `observedAt` | 발생 시각과 별도로 저장 |
| `metadataEvidence` | 필드 값을 확인할 수 있는 자료·구간 |

LLM이 추정한 빈 필드를 확인된 값처럼 채우지 않는다. 연결 규칙은 사건 유형별 버전으로 관리한다.

### 규칙 종류

- `SAME_EVENT`: 필수 식별 키·역할·행위가 맞고, 시간 구간의 **전체 공통 부분** 등 규칙을 충족해야 한다.
- `ORDERED_EVENTS`: 선후 사건의 대상 키가 이어지고 지정한 시간 순서를 만족해야 한다. 서로 다른 사건을 같은 시각으로 맞추지 않는다.
- `SAME_ENTITY`: 사건 시각이 달라도 정의된 동일 객체 연결 규칙을 만족할 수 있다.

자료 A–B, B–C가 각각 겹친다고 A–B–C 전체가 일치한다고 가정하지 않는다. 예를 들어 시각 구간 `[1,3]`, `[3,5]`, `[5,7]`은 인접 구간끼리 닿지만 전체 공통 시각은 없다.

<EventIntervals number="F3" />

<Equation number="F4" label="닫힌 시각 구간들의 전체 교집합" tex={String.raw`\bigcap_i [\ell_i,u_i]\ne\varnothing\quad\Longleftrightarrow\quad\max_i\ell_i\le\min_i u_i`} />

이 식은 같은 시간대와 정밀도로 정규화한 닫힌 구간의 조건이다. 열린 경계나 허용 오차는 사건 규칙에 별도로 명시한다.

| 결과 | 처리 |
| --- | --- |
| `MATCH` | 해당 후보를 유지 |
| `MISMATCH` | 후보를 제외하고 `EVENT_MISMATCH`. 충돌한 필드·기대값·관측값 기록 |
| `UNKNOWN` | 지지 체인으로 확정하지 않음. 부족한 메타데이터를 `EVIDENCE_INSUFFICIENT`로 기록하고 보류 |

UNKNOWN을 MISMATCH로 바꾸지 않는다. 실제 불일치만 연결 불가로 설명한다. 자료 자체를 삭제하지 않으며 다른 주장·사건에는 적합할 수 있다.

## 1-6 · 부모 단위 중복 자료 검사

부모 노드를 하나의 비교 단위로 삼고 그 아래 증거 binding의 중복을 검사한다. LLM은 같은 사건·같은 주장을 뒷받침하는 동일 내용인지, 일부 겹침인지, 독립 관측인지 판정한다.

1. 동일 content hash·기록 ID 등으로 완전히 같은 자료를 먼저 식별한다.
2. 같은 부모의 나머지 후보에 관련 구간·사건 메타데이터·원출처를 제공해 LLM 판정을 요청한다.
3. 판정에 원문 위치와 이유를 요구하고 코드가 응답 구조·참조를 검증한다.
4. `EXACT_DUPLICATE` 또는 근거가 확인된 `SAME_OBSERVATION`만 같은 evidence atom으로 묶는다.
5. `PARTIAL_OVERLAP`, `DISTINCT`, `UNKNOWN`은 보존한다. 불확실한 중복을 임의로 제거하지 않는다.
6. requirement별 충족 정보가 같은 후보만 대표 후보로 합친다. 제외한 자료는 `duplicateOf`와 사유로 남긴다.

대표 자료는 원문 접근 가능성·구간 완전성 등 버전 있는 규칙으로 선택하고, 동률은 안정된 ID 순서로 정한다. 신뢰도가 높아 보이는 자료만 남겨 반증을 지우지 않는다.

LLM의 쌍별 “유사” 판정은 전이적이라고 보장되지 않는다. A≈B, B≈C만으로 A·B·C를 모두 병합하지 않고 대표 관측과의 동등성을 다시 검사한다.

부모별 중복 축소 후에도 전체 루트의 신뢰도 계산에서는 **부모를 가로지르는 공유 evidence atom과 출처 의존성**을 확인한다. 국소 중복 제거만으로 전역 독립성이 확보되지는 않는다.

## 1-7·1-8과 최종 공백

[출처 계보와 신뢰도](/docs/main-algorithm/confidence)에서 계보 추적, D/E 처리, AND·OR 집계를 수행한다. 평가가 완료되었는데 목표까지 연결 가능한 적격 체인이 하나도 없으면 `CHAIN_UNKNOWN`을 상세 원인 gap에 연결한다.

이 지침에서 체인 완성은 **필수 연결과 자료 적격성이 갖춰져 신뢰도 평가가 가능한 상태**로 구체화한다. 완성된 체인의 점수가 약하면 `TRUST_WEAK`이며, 점수가 낮다는 이유만으로 자동으로 `CHAIN_UNKNOWN`을 중복 생성하지 않는다. 수치 신뢰도와 연결 완성도를 별도 축으로 유지하기 위한 규칙이다.

## OR 대안의 공백과 전체 결론의 구분

한 OR 가지가 탈락했지만 다른 가지가 목표를 지지하면 탈락 사유는 `blockingScope=ALTERNATIVE`로 기록한다. 전체 결론이 막혔다고 표시하지 않는다. 반대로 AND 필수 요구의 공백은 상위 경로를 따라 ROOT까지 영향을 줄 수 있다.

모든 탈락 사유를 보존하되 동일한 원인·requirement·자료·실행 버전의 gap은 한 번만 기록한다. `CHAIN_UNKNOWN`은 원인 요약이므로 구체적인 부족 자료 설명을 대체하지 않는다.

## 비용과 결정성

후보 수는 OR 대안 수의 곱으로 지수적으로 증가할 수 있다. 단계별 pruning·메모이제이션·지연 평가를 사용하고, 중단한 범위를 명시해야 한다. 부모에 자료가 `k`개면 모든 쌍의 중복 검사는 `O(k²)` 호출 후보를 만들 수 있으므로 해시와 사건 조건으로 비교 대상을 먼저 줄인다.

<Equation number="F5" label="부모별 전수 쌍 비교의 후보 수" tex={String.raw`N_{\mathrm{comparisons}}=\sum_{p}\binom{d_p}{2}`} />

같은 snapshot·규칙·이미 저장된 판정으로 재평가하면 코드의 결과는 동일해야 한다. LLM을 새로 호출하면 결과가 달라질 수 있으므로 응답과 판정 버전을 보관한다.
