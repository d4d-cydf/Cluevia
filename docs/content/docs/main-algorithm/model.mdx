자료를 하나의 노드로 표현하는 방식만으로는 그 자료가 어느 주장의 어떤 조건을 충족하는지 충분히 기술하기 어렵다. 이를 명시하려면 자료 자체, 검증할 주장, 둘 사이의 연결 판정을 분리해야 한다. 본 절은 이 구분을 바탕으로 Why-not Tree의 저장 단위와 참조 제약을 정의한다. 아래 타입은 개념을 설명하기 위한 설계 계약이며, 현재 구현의 대응 계약은 `src/types/why-not.ts`에서 관리한다. 확장 자료 형태와 정책 제안의 구현 여부는 별도로 구분한다.

## Why-not Tree의 의미

루트는 검증할 주장이다. 내부 노드는 하위 주장과 AND·OR·NOT_SUPPORT 연산을 표현한다. 최하위 evidence leaf는 실제 자료의 특정 구간을 참조한다. 아직 없는 자료는 실제 leaf로 만들지 않고 **증거 요구**로 남긴다.

<ResearchDiagram kind="tree" number="M1" />

<Equation number="M1" label="상위 주장을 구성하는 필수 조건" tex={String.raw`H=C_1\land C_2=(L_1\lor L_2)\land C_2`} />

여기서 부모는 leaf가 아니라 **주장 또는 연산 노드**다. 화면에서 나무로 펼쳐도 저장 구조는 같은 자료 참조를 공유하는 DAG가 될 수 있다. 순환하는 주장 의존성은 허용하지 않는다. 별도의 출처 인용 그래프에서는 순환을 발견해 기록하고 탐색을 종료한다.

## 자료 형태와 출처 평가의 구분

| 필드 | 역할 | 예 |
| --- | --- | --- |
| `artifactKind` | leaf의 자료 형태 | `DOCUMENT`, `STRUCTURED_RECORD`, `IMAGE`, `AUDIO`, `VIDEO`, `WEB_PAGE`, `OTHER` |
| `mimeType`, `format` | 실제 파일 형식 | `text/csv`, PDF, JSONL, PNG |
| `sourceType` | 발행·생성 주체와 자료 성격 | 원본 업무기록, 직접 관측, 재인용 기사 |
| `sourceGrade` | 출처 평가 등급 | A/B/C/D/E 또는 미평가 |
| `verdict` | 특정 주장을 지지하는지 | `SUPPORTED` 등 |

자료 형태 enum과 등급의 세부 정의는 제안이다. 현재 앱의 원본 분석은 UTF-8 텍스트 중심이므로 PDF·이미지·음성 등을 leaf 타입으로 설계했다고 추출 기능까지 구현된 것은 아니다. 추출 전에는 `processingStatus`로 대기 상태를 보존한다.

## 논리 노드와 증거 요구

```ts
type LogicOperator = 'AND' | 'OR' | 'NOT_SUPPORT';

type LogicNode = {
  id: string;
  kind: 'claim' | 'requirement';
  statement: string;
  operator: LogicOperator;
  children: string[]; // 논리 노드 또는 evidence binding의 ID
  eventRuleId: string | null;
  threshold: number | null; // null이면 별도 하위 임계값 없음
  negativeOf: string | null; // NOT_SUPPORT가 입증할 부정 대상
};

type EvidenceNeed = {
  requirementId: string;
  targetClaimId: string;
  acceptableKinds: string[];
  requiredFields: string[];
  acceptanceCriteria: string[];
  eventScopeId: string;
};
```

`claim`의 children이 비어 있으면 잘못된 논리 설계다. `requirement`는 아직 자료가 없어 비어 있을 수 있으며 이때 `EVIDENCE_MISSING`으로 기록한다. AND의 필수 requirement를 삭제해서 더 약한 주장으로 바꾸지 않는다.

AND·OR은 어떤 증거 조합이 충분한지를 사전에 설명해야 한다. “수령증 OR 로그”라고 쓰려면 각각 단독으로 어떤 하위 주장을 충족하는지 정의한다. “자료가 둘 있다”는 이유로 OR을 자동 선택하지 않는다.

## NOT_SUPPORT의 의미와 적용 조건

**정의:** NOT_SUPPORT는 부정 주장을 입증하는 증거들의 AND 결합이다.

예를 들어 “마감 시각 전에 취소되지 않았다”를 주장하려면 대상 식별, 전체 확인 기간, 취소 기록의 완전성, 해당 기간의 결과 등 필요한 조건을 각각 입증하도록 분해한다. 부분 로그에서 취소 항목을 못 찾았다는 이유만으로 통과시키지 않는다.

```text
NOT_SUPPORT(취소되었다)
  = AND(대상 일치, 확인 구간 충족, 기록 완전성, 취소 없음의 직접 근거)
```

<ResearchDiagram kind="negative" number="M2" />

<Equation number="M2" label="부정 주장에 필요한 조건의 결합" tex={String.raw`\operatorname{NOT\_SUPPORT}(H)=\bigwedge_{i=1}^{n} C_i^{-}`} />

여기서 Cᵢ⁻는 부정 주장을 입증하기 위해 명시한 필수 조건이다.

이 규칙은 확률의 여사건 계산 `1 − P(A)`를 사용하는 NOT와 다르다. 신뢰도도 확보된 **부정 주장 지지 자료들**을 AND로 결합한다. 필요한 자료가 없으면 공백이다.

## Evidence와 Binding

Evidence는 자료 자체, Binding은 그 자료가 특정 주장의 어떤 요구를 지지하는지 나타낸다. 판정은 자료 전체의 고정 속성 대신 **binding 단위**로 저장한다.

<ResearchDiagram kind="binding" number="M3" />

```ts
type Evidence = {
  id: string;
  artifactKind: string;
  contentHash: string;
  sourceId: string;
  sourceUrl: string | null;
  capturedAt: string;
  processingStatus: 'READY' | 'PENDING' | 'FAILED';
};

type EvidenceBinding = {
  id: string;
  evidenceId: string;
  parentClaimId: string;
  requirementId: string;
  locator: { kind: 'text' | 'row' | 'page' | 'time'; value: string };
  quote: string | null;
  decisionId: string | null;
  eventMetadataId: string | null;
  evidenceAtomId: string | null;
};
```

`locator`는 텍스트 offset·행 ID·페이지·영상 시각 등을 표현한다. 실제 구현에서는 종류별 유효성 검사를 추가한다. 하나의 문서가 두 requirement를 충족할 수 있지만, 두 binding이 동일한 관측을 사용하면 신뢰도 계산에서 독립 증거 두 개로 세지 않는다.

## 자료 판정 enum과 현재 구현의 관계

아래 enum은 자료–주장 적합성 판정의 계약이다. **`SUPPORTED`만 적합성 관문을 통과**하는 규칙은 확정 요구다.

| 값 | 의미 | 1-4 처리 |
| --- | --- | --- |
| `SUPPORTED` | 이 구간이 해당 하위 주장을 정해진 기준만큼 지지 | 통과 |
| `REFUTED` | 이 구간이 해당 주장에 반하는 내용을 제시 | 부적격, 반증 별도 보존 |
| `INSUFFICIENT` | 관련은 있으나 요구한 사실을 입증하지 못함 | 부적격, 부족한 필드 설명 |
| `IRRELEVANT` | 해당 주장·요구와 직접 관련 없음 | 부적격, 관련 없는 이유 설명 |
| `UNREVIEWED` | 판정이 완료되지 않음 | 아직 통과 불가, 평가 미완료 표시 |

판정 기록에는 `bindingId`, `verdict`, `reason`, `supportingLocators`, `missingRequirements`, `evaluator`, `modelVersion`, `promptVersion`, `createdAt`을 포함한다. `SUPPORTED`도 근거 구간과 사유를 요구한다. 원문 없는 자유 서술은 판정 결과로 수락하지 않는다.

현재 앱의 `reported/inferred`, `claim.stance`, 사용자 검토 `supported/disputed/needs-review/unreviewed`는 서로 다른 의미다. 예를 들어 “부인했다는 진술이 존재한다”는 주장은 `claim.stance=denied` 자료로 지지할 수 있다. 현재 enum을 새 적합성 판정으로 무조건 복사하지 않는다.

반증은 지지 집합에서 제외하되 진단·화면에는 유지한다. 반증이 같은 목표와 사건을 직접 충돌시키면 자동 확정 대신 `EVIDENCE_INSUFFICIENT`의 `CONTRADICTORY_EVIDENCE` 사유로 검토 대상으로 남기는 것을 구체화 규칙으로 둔다.

## 후보 집합의 식별과 동등성

집합 트리는 원래 Why-not Tree에서 **한 가지 성립 경로를 택한 후보**다. 단순한 자료 ID 집합만으로 저장하면 어느 requirement를 충족했는지 잃으므로 다음을 보존한다.

```ts
type WitnessTree = {
  id: string;
  treeVersion: string;
  chosenBranches: Record<string, string[]>;
  bindingsByRequirement: Record<string, string[]>;
  evidenceIds: string[];
  eventConstraintResults: string[];
  status: 'ACTIVE' | 'REJECTED' | 'PENDING';
  rejectionGapIds: string[];
};
```

같은 자료 ID 집합이어도 requirement 연결이나 사건 역할이 다르면 같은 후보로 합치지 않는다. 대표 후보에서 제외한 트리는 삭제하지 않고 상태와 탈락 단계를 기록한다.

## Gap 기록

```ts
type GapType =
  | 'EVIDENCE_MISSING' | 'EVIDENCE_INSUFFICIENT' | 'EVENT_MISMATCH'
  | 'TRUST_WEAK' | 'PROVENANCE_UNKNOWN' | 'CHAIN_UNKNOWN';

type Gap = {
  id: string;
  runId: string;
  type: GapType;
  stage: '1-3' | '1-4' | '1-5' | '1-7' | '1-8' | 'FINAL';
  claimId: string;
  requirementIds: string[];
  witnessIds: string[];
  evidenceIds: string[];
  reasonCode: string;
  explanation: string;
  expected: unknown;
  observed: unknown;
  blockingScope: 'ALTERNATIVE' | 'SUBCLAIM' | 'ROOT';
  causeGapIds: string[];
  evaluationState: 'COMPLETE' | 'PENDING';
};
```

사유 문자열만 남기지 말고 기대값과 관측값을 함께 저장한다. 여러 gap이 동시에 생길 수 있으며 `CHAIN_UNKNOWN`은 상세 gap을 덮어쓰지 않고 `causeGapIds`로 연결한다.

## 실행과 결과 버전

한 실행은 `treeVersion`, `evidenceSnapshotId`, `decisionVersion`, `eventRuleVersion`, `trustPolicyVersion`을 고정한다. 실행 도중 찾은 새 증거는 다음 snapshot 후보다. 원래 자료·판정·결과를 덮어쓰지 않는다.

<Equation number="M3" label="한 실행에서 고정할 버전 묶음" tex={String.raw`S_t=(v_{\mathrm{tree}},v_{\mathrm{evidence}},v_{\mathrm{decision}},v_{\mathrm{event}},v_{\mathrm{trust}})`} />

결과에는 다음 세 값을 별도로 저장한다.

| 값 | 상태 |
| --- | --- |
| `evaluationStatus` | `COMPLETE`, `INCOMPLETE`, `FAILED` |
| `chainStatus` | `COMPLETE_CHAIN_FOUND`, `NO_COMPLETE_CHAIN`, `UNDETERMINED` |
| `confidence` | 점수 또는 구간, 계산 가정, 임계값, 충족 여부 |

숫자를 계산할 수 없을 때 `null`과 이유를 사용한다. 미평가를 0이나 1로 채우지 않는다.
