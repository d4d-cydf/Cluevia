<Abstract keywords={"基于证据的推理 · Why-not Tree · 证据缺口诊断 · 来源谱系 · 不确定性"}>

仅提取资料之间的关系，并不足以说明得出特定结论还缺少什么。Cluevia 将目标主张分解为逻辑条件和证据要求，并从结构上诊断现有资料未能满足要求的位置。所提出的流程包括构建 Why-not Tree、通过 Gap Find 评估候选证据组合，以及通过 Gap Fill 生成有针对性的证据补充要求。系统分别评估资料是否存在、资料对主张的适合程度、事件一致性、来源可核查性与支持程度，避免将复用同一观测的资料重复计为独立证据。本文规定其形式化契约与实现范围。数值输出是在明确模型与策略下计算的支持分数；未经单独校准，不能将其解释为结论为真的概率。

</Abstract>

## 1. 引言 [#1-서론]

证据审查的困难不仅在于资料量，还在于资料与结论之间的逻辑距离。例如，预计交付通知不能证明实际交付已经完成，多篇转引同一新闻稿的文章也不等于多次独立观测。即使对象和关系提取准确，若未表达这些区别，界面连线的密集程度仍可能被误认为结论成立的程度。

Cluevia 的核心问题是：**依据现有资料与明确的推理规则，是否已形成支持目标主张的路径；若尚未形成或无法确认，还需要在何种条件下取得哪些资料？** 因此，首要输出是一组证据关联、评估状态、缺口原因与补充请求，而非单句结论。

这一设计强调三项区分：资料存在与资料足以支持主张；某条替代路径失败与整个目标没有支持路径；完成检查后的不合格判定与资料或计算预算不足导致的暂缓判定。这些区分既解释缺口，也界定后续取证范围。

## 2. 问题定义与记号 [#2-문제-정의와-표기]

以 E 表示当前取得的资料集合，T 表示逻辑结构，Π 表示判定、事件与可信度策略。一次评估固定这些输入的版本，形成快照；执行中取得的新资料作为下一快照的候选输入。

| 标志 | 的意思 |
| --- | --- |
| H | 目标与指定的目标，行动，期限和范围要求 |
| E | 包含可检查的实际文本或记录部分的数据集 |
| T | 由主张、证据要求及逻辑运算符组成的有向无环结构 |
| b | 绑定将特定数据部分与证据要求联系起来 |
| F(v) | 一组可以构建以满足节点v的需求的候选结合集。 |
| W | 通过适合性、事件一致性及来源关卡的论证路径集合 |
| G | 包含阶段、原因和影响范围的缺口记录集合 |
| s(v) | 在明确策略下计算的支持分数；未知时为 null |
| Π | 判定规则、可信度假设、阈值、探索预算及其版本 |

**定义 1——证据要求与证据资料。**证据要求说明哪些事实须被核实，证据资料则指可供检验的实际记录。要求存在并不意味着已取得资料。未读取正文的 URL、文件名或搜索结果标题，均不能单独构成证据 leaf。

**定义 2——binding。**适合性判定的单位是资料片段与特定要求之间的关联，而不是整份资料。同一文档可能足以支持一项主张，却不足以支持另一项主张。binding 须同时保存引文位置、判定、理由与判定版本。

界面可以按树展开，但同一资料或观测可能被多处引用，因此存储与计算采用保留共享结构的 DAG。来源引用中的循环在独立谱系图中记录并终止追踪。具体类型与引用规则见[树结构模型与数据契约](/zh/docs/main-algorithm/model)。

## 3. 方法 [#3-방법론]

<ResearchPipeline />

### 3.1. 构建目标主张与逻辑结构 [#31-목표-주장과-논리-구조의-구성]

先将问题规范化为可检验的主张，再说明其成立所需的子条件。不得以检验较弱的主张来替代原问题。“已交付”与“已通知计划交付”是不同的主张。

每个内部节点均须指定 AND、OR 或 NOT_SUPPORT 运算子及明确的推理规则。AND 要求全部必要条件成立；OR 要求至少存在一条合格的替代路径。NOT_SUPPORT 定义为**用于证明否定命题的证据的 AND 组合**。它既不把搜索无结果视为否定证据，也不执行补事件概率的计算。

LLM 提出子主张及判定候选，代码负责验证引用、原文位置与逻辑结构，并执行最终计算。这样既使用模型的语义解释能力，也避免自由文本描述绕过验证。

### 3.2. 从现有资料构造候选组合 [#32-현재-자료로-가능한-후보의-구성]

步骤 1-3 仅使用当前已取得的 binding。OR 节点的候选族为子节点候选族的并集；AND 节点则从每个子节点各选一个候选，再组合为一项候选。下式中 cᵢ 表示子节点，wᵢ 表示对应子节点的候选。

<Equation number="1" label={"候选组合 AND 和 OR "} tex={String.raw`\begin{aligned} F_{\mathrm{OR}}(v)&=\bigcup_i F(c_i)\\ F_{\mathrm{AND}}(v)&=\left\{\bigcup_i w_i\;\middle|\;w_i\in F(c_i)\;\forall i\right\}\end{aligned}`} />

<CandidateMatrix number="3" />

尚无资料的必要要求，其候选集合为 ∅。AND 的任一必要子节点为 ∅ 时，父节点的候选集合也为 ∅。不能将其与 `{∅}` 混淆；后者表示一个仅凭空证据即可成立的候选。也不允许删除缺失条件来弱化 AND。

即使无法构造根候选，也可保留现有资料的局部诊断。例如，其他必要条件缺失时，仍应指出预计交付通知不能证明实际完成。局部诊断存在与完整支持路径存在须分别报告。

### 3.3. Gap Find 的分阶段评估 [#33-gap-find의-단계별-평가]

表 1 给出阶段判定与输出之间的关系。1-3、1-4、1-5、1-8 沿用原设计编号，其余编号用于完整描述流程。

| 步骤 | 评估目标 | 判断和后续行动 |
| --- | --- | --- |
| 1-1·1-2 | 目标和逻辑 | 确定事件范围和证据要求，并验证逻辑结构。 |
| 1-3 | 实际数据的存在 | 组织候选人。 如果所需数据不存在，请记录 `EVIDENCE_MISSING` . |
| 1-4 | 资料对主张的适合性 | 只有 `SUPPORTED` 已经通过了。 其他原因被保存并诊断为 `EVIDENCE_INSUFFICIENT` . |
| 1-5 | 候选人之间一致的事件 | 应用特定的元数据规则。 实际碰撞被归类为 `EVENT_MISMATCH` ,未知的碰撞被归类为正在进行评估。 |
| 1-6 | 每个父节点的重叠观察 | 识别相同的数据和相同的观察，但不要任意将不确定的重复合并。 |
| 1-7 | 来源与引用谱系 | 核查原始来源及共享观测；来源为 D/E 时记录 `PROVENANCE_UNKNOWN` |
| 1-8 | 整体逻辑的支持程度 | 计算时保留共享证据与依赖；无法确认充分性时记录 `TRUST_WEAK` |
| 最终确认 | 评估完整性和路径 | 如果评估完成，但没有完成的途径，记录 `CHAIN_UNKNOWN` . |

*表 1. Gap Find 的判定关卡。详细规则见 [Gap Find 分阶段评估](/zh/docs/main-algorithm/gap-find)。*

若资料不合格，则排除必须依赖该资料的候选组合。继续评估 OR 的其他替代路径，并在原始记录中保留反证及排除理由。不能将 `UNREVIEWED`、模型调用失败或事件元数据未知，视为已完成的反证判定。

去重时，观测是否相同比文件数量更重要。两份转录同一原文的文档虽是两个文件，却可能共享同一观测。LLM 的去重建议须结合原文和理由审查；确认同一观测后，通过共享 atom 关联。

### 3.4. 来源谱系与可信度聚合 [#34-출처-계보와-신뢰도-집계]

在所用模型中，新增资料的条件似然比为 1 时，不改变已有观测下的相对支持，因此保留原资料，不将新增资料计为独立支持。似然比不为 1 时，继续核查引用谱系，直至满足原始来源条件或达到有限预算。缺少似然估计模型时须记录未知，不能替换为 1。似然比的解释依赖模型选择与不确定性审查。[Lund 与 Iyer，2017](https://doi.org/10.6028/jres.122.027)。

下列可信度乘积公式仅适用于可将子节点支持程度建模为相互独立的情形。独立性也是串联、并联可靠性模型使用相应公式的前提。[NIST 串联模型](https://www.itl.nist.gov/div898/handbook/apr/section1/apr182.htm)、[NIST 并联模型](https://www.itl.nist.gov/div898/handbook/apr/section1/apr183.htm)。

<Equation number="2" label={"根据独立假设的支持分数汇总"} tex={String.raw`\begin{aligned}s_{\mathrm{AND}}(v)&=\prod_i s(c_i)\\s_{\mathrm{OR}}(v)&=1-\prod_i\bigl(1-s(c_i)\bigr)\end{aligned}`} />

<ResearchPlot kind="support-curves" number="5" />

来源 URL 不同并不能证明独立性。尤其是 `(a AND b) OR (a AND c)` 中的两条路径共享 a，因此不能对路径分数直接应用独立 OR 运算。在说明性模型中，若 a、b、c 为相互独立的观测，分数分别为 0.8、0.7、0.6，保留共享变量得到 0.704；将两条路径误视为独立则会高估为 0.7712。

这些数值仅用于说明计算结构。产品策略指定的来源和资料系数相乘后，不会自动成为校准概率。独立性不明或系数未知时，应返回符合假设的保守范围或 null。终止规则及详细计算见[来源谱系与可信度](/zh/docs/main-algorithm/confidence)。

### 3.5. 填补缺口和重新评估 [#35-gap-fill과-재평가]

Gap Fill 不应机械重复搜索，而应从各缺口提取未满足条件，请求能够检验该条件的资料类型、标识符、时间与来源。下表是设计规定的对应行动，自动互联网搜索及原文获取须与当前实现范围区分。

| 证据缺口 | 补充的目标 | 应对行动 |
| --- | --- | --- |
| `EVIDENCE_MISSING` | 缺少资料的必要要求 | 搜索直接资料；无法公开取得时，请用户提供所需资料 |
| `EVIDENCE_INSUFFICIENT` | 数据不符合的事实和条件 | 解释文本与目标之间的不一致性，并要求提供更多证据。 |
| `EVENT_MISMATCH` | 结合规则中的矛盾价值观 | 呈现不一致的对象，时间，位置等，并解释连接的不合格性。 |
| `TRUST_WEAK` | 支持程度的瓶颈 | 没有足够的连接以迷你图表表示，并要求补充证据。 |
| `PROVENANCE_UNKNOWN` | 未确认的来源 | 要求原始来源的注释或寻找可验证的谱系。 |
| `CHAIN_UNKNOWN` | 一个未完成的目标之路 | 我们提出了三个链接完成策略，包括所需的数据类型。 |

*表 2. 缺口类型与补充请求的对应关系。*

搜索或添加资料本身不能证明缺口已经消除。新增资料须在独立版本中重新接受存在性、适合性、事件、来源及可信度检查。修改目标或逻辑结构时，还须更新树版本。[Gap Fill 行动指南](/zh/docs/main-algorithm/gap-fill)规定各行动的输入、完成条件与终止规则。

## 4. 结果解释与计算约束 [#4-결과의-해석과-계산상의-제약]

评估结果应从三个维度解读：**论证路径状态、支持程度和评估完备性**。完整路径的存在并不保证支持程度达到阈值。反之，在评估尚未完成时，未找到路径也不能证明不存在任何路径。这些状态本身均不意味着目标主张为假。

<ResultMatrix number="6" />

候选枚举成本取决于逻辑分支数。即便在简单的 AND–OR 结构中，若 m 项必要条件各有 k 个选项，也可能产生最多 kᵐ 个组合。对父节点 p 下的 dₚ 份资料进行全部两两比较，需要 dₚ(dₚ−1)/2 次比较。共享 atom 的加权逻辑评估在最坏情况下也可能开销较大。这些表达式描述组合结构的成本，并不构成“实测运行时间始终与该上界成正比”的经验性结论。

<Equation number="3" label={"不同的替代组合和父节点特定的比较对。"} tex={String.raw`\begin{aligned}|F(H)|&=\prod_{i=1}^{m} k_i\quad(=k^m\text{ if }k_i=k)\\N_{\mathrm{pairs}}(p)&=\binom{d_p}{2}=\frac{d_p(d_p-1)}{2}\end{aligned}`} />

<ResearchPlot kind="candidate-growth" number="7" />

因此，应明确候选数、状态数、访问次数与深度预算，并在达到预算时记录尚未评估的范围。缓存与惰性评估用于降低开销，不能成为删除必要要求或把未完成状态改为完成的依据。可以报告已经确认的路径存在；要确定路径不存在，则必须完成作出该判定所需的评估。

## 5. 实现范围与验证 [#5-구현-범위와-검증]

### 5.1. 目前实施范围 [#51-현재-구현의-범위]

当前实现可根据已完成或失败案例的存档资料，提出逻辑结构和引文判定；通过契约验证后，执行候选评估、缺口生成、原文搜索、用户补充及版本化重新评估。外部搜索提供方的自动采集与网络范围溯源尚未接入。

自动逻辑生成使用有限摘录，不能假设已经阅读全部资料。来源系数、阈值和独立性也作为可审查的输入假设管理。模块职责、API 与验收案例见[实施步骤与验收标准](/zh/docs/main-algorithm/implementation)。

### 5.2. 评估设计 [#52-평가-설계]

该算法的合同验证和其对实际数据的意义判断的准确性必须单独进行评估。 前者可以通过复制式检查固定快照来证实。 后者需要确定判断标准的评估数据和独立审查。 下列项目是评估计划，并不意味着尚未报告的准确性或改善率。

| 评估问题 | 观察点 | 比较和控制 |
| --- | --- | --- |
| 正确检测缺失的先决条件 | 证据缺口匹配类型，影响范围和原因路径 |  AND / OR / NOT_SUPPORT 确定的正确答案条件 |
| 是否避免将未完成误判为不存在？ | 评估状态与链状态 | 注入预算耗尽、未审查与未读取的情形 |
| 复制观察不会提高你的分数吗? | 分享原子数量和支持分数的变化 | 复制和重复相同的原始文本之前和之后的比较 |
| 是否保留事件关联规则？ | 期望值、观测值与冲突原因 | 同名、不同标识符及时刻冲突的案例 |
| 实际决定是合理的吗? | 审查者关于合适性，反证据，证据缺口的协议 | 单独的实际数据评估，对差异的调整程序 |
| 运行成本是否可接受？ | 各阶段延迟、调用次数、token 数与缓存命中 | 固定资料规模、格式、模型和策略后重复执行 |

### 5.3. 辅助处理时间的观测 [#53-보조-처리-시간의-관찰]

仓库保存了一项单输入观测，仅测量**评估前的本体设计与模式验证阶段**。188 字符输入下，旧版 high 设置约耗时 121.9 秒；使用 medium、简洁模式与提示的新运行约耗时 84.1 秒。相同设计输入命中缓存后，无新增模型调用，约在 1.67 ms 内完成。这不衡量完整抽取、Gap Find 的总耗时，也不衡量语义准确性。

该比较同时改变了多项设置，基线运行也来自历史记录。因此，不能将观察到的差异归因于 effort 单一因素，也不能据此预测其他输入的处理时间。测量范围与复用条件见[本体设计与抽取文档](/zh/docs/algorithms/extraction)。原始数值及限制保存在仓库的 `docs/evaluations/ontology-design-medium-cache.json` 中。

## 6. 讨论和限制 [#6-논의와-한계]

首先要考虑的限制是逻辑结构本身是否合适。 即使你正确计算一个不良设计的证据要求，结果并不能提供适当的答案。 因此，推断规则和事件范围必须能够被阅读和修改，模型提出的结构不排除审查。

第二项局限是观测与来源之间的依赖。格式或发布主体不同的资料仍可能共享同一观测，一份文档内也可能同时存在共享内容与独立新增观测。无法确认这些区别时，应优先如实表达未知与范围，而非追求单一分数的表面精度。

第三项局限涉及数值的解释。来源等级和资料质量系数本身并不是统计估计量。若要将其解释为结论为真的概率，还需要单独建模、校准及验证数据。本文不声称已完成这类验证。

最后，缺口补充不保证成功。非公开记录、无法访问的原文及无法恢复的时间信息可能始终无法核实。此时系统的职责是说明剩余条件与搜索范围，而不是强行给出结论。

## 7. 结论 [#7-결론]

Cluevia不仅展示了数据关系，还记录了必要的连接到目标主张以及尚未满足的条件。 这种方法的实际意义是追踪判断的基础，并确定下一次审查的目标。 未来的评估应验证逻辑设计和意义确定的实际准确性，支持分数的可解释性以及补充要求在调查过程中的有用性。
