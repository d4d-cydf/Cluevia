# 대용량 자료와 온톨로지 기반 처리

새 분석은 **Codex가 자료에 맞는 온톨로지를 설계하는 단계**로 시작합니다. 검증된 구조화 데이터는 코드로 변환하고, 문서는 Codex로 추출합니다. Jev는 제한된 선택지로 표현할 수 있는 판정에만 사용합니다.

## 연결 설정

서버를 실행하는 OS·사용자 계정에서 먼저 Codex에 로그인합니다.

```powershell
npm run codex:login
npm run codex:status
```

Jev를 함께 쓰려면 `.env` 또는 `.env.local`에 아래 값을 설정합니다. 기존 파일과 키를 덮어쓰지 마세요.

```dotenv
TYPESAFE_API_KEY=여기에_TypeSafe_API_키
TYPESAFE_MODEL=jev-1.13.0
TYPESAFE_CONCURRENCY=4
TYPESAFE_TIMEOUT_MS=30000
TYPESAFE_MIN_CONFIDENCE=0.85
```

변경 후 `npm run dev`를 다시 실행합니다. `.env.local`에 빈 `TYPESAFE_API_KEY=`가 있으면 `.env`의 실제 키를 가릴 수 있으므로 키를 한 파일에서 관리하세요. 키는 서버에서만 읽으며 `VITE_` 접두사를 붙이지 않습니다. 홈의 **Jev 선택 판정 준비됨**은 설정이 있다는 뜻이며, 실제 권한·사용량·연결은 호출 시 확인합니다.

새 분석에서는 표 데이터도 최초 설계에 Codex를 사용합니다. Jev 키가 없어도 Codex 경로로 분석할 수 있습니다. 저장된 온톨로지와 그래프 열기는 모델 연결이 필요 없습니다.

## 1. 자료에 맞는 구조 설계

Codex는 질문과 자료의 프로필·제한된 예시를 바탕으로 다음을 설계합니다.

- 객체 유형과 속성: 이름, API 이름, 기본 타입, 필수 여부, 기본 키, 표시 이름.
- 관계 유형: 출발·도착 객체 유형, 방향, 개수 제약.
- 공유 속성·인터페이스·Value Type·객체 유형 그룹.
- 구조화 파일의 컬럼 매핑과 식별 기준.
- 문서 처리 전략과 Jev에 적합한 관계 유형, 의미 분석 열에 반복 적용할 선택형 질문.

구조화 파일은 전체 레코드를 읽어 컬럼과 형식을 확인하되 모델에는 한도가 있는 프로필과 예시를 전달합니다. 설계 단계가 원본 전체의 모든 의미를 읽는 것은 아닙니다. 이후 실제 변환·분석은 모든 구간을 처리합니다.

생성된 정의는 참조·타입·제약을 검증한 후 ID·버전과 함께 저장합니다. 중단한 작업을 재개하면 같은 정의를 사용합니다. **질문만 입력하면 구조만 저장**하고 종료합니다. 자료 없이 실제 객체나 관계를 만들지 않습니다.

Action Type과 Function은 실행되지 않는 초안 메타데이터입니다. 미디어·첨부·시계열·마킹·암호화 타입도 참조 값의 계약이며, 해당 외부 시스템이나 권한·암호화 엔진을 구현하는 기능은 아닙니다.

## 2. 자료별 변환

| 자료 | 처리 |
| --- | --- |
| `.csv`, `.tsv` | 헤더와 행을 읽고 이번 온톨로지의 컬럼 매핑으로 변환 |
| `.jsonl`, `.ndjson` | 비어 있지 않은 각 줄의 JSON 레코드를 매핑 |
| `.json` | 최상위 배열·객체 또는 최상위 객체 필드의 레코드 배열을 해석 |
| 기타 UTF-8 문서 | 크기가 제한된 구간을 생성된 스키마에 맞춰 Codex로 분석. 조건이 맞을 때만 Jev 판정 |

구조화 처리 여부는 첨부 파일의 확장자로 정합니다. 표를 직접 붙여 넣으면 일반 문서로 취급하므로 행 단위 변환을 사용하려면 CSV·JSON 파일로 첨부하세요.

검증된 매핑으로 변환할 수 있는 행은 **행마다 모델을 호출하지 않습니다.** 원문에 없는 관계나 객체를 컬럼 이름만으로 임의로 덧붙이지 않습니다. 매핑이 없거나 안전하게 적용할 수 없는 부분은 Codex 분석으로 처리합니다. 잘못된 CSV·JSON 문법은 오류를 보고하며, 원본 전체는 저장소에 유지합니다.

원본에 행 ID가 없어도 `evidenceId`를 기본 키로 선언한 관측·기록은 서버가 안정적인 키를 만들고 직접 변환합니다. 동일한 내용의 행도 원본 순번으로 구분하며, 이 순번은 서버가 붙인 메타데이터라고 표시합니다. 실제 업무 식별자를 추측하지 않습니다. 정상 행은 최대 100행씩 묶고, 예외 행은 최대 8행씩 모델에 전달합니다.

본문·설명처럼 추가 의미를 읽어야 하는 열은 `sourceMappings[].semanticColumns`로 지정합니다. 식별자 등 정형 필드는 먼저 저장하고, 지정한 열이 있는 원본 행 전체를 별도로 분석합니다. 긴 본문을 500자짜리 속성으로 잘라 저장하거나, 표 안에 있다는 이유로 분석을 생략하지 않습니다. 설계 단계는 누락된 열 매핑을 한 번 보완하며, 여전히 매핑하지 못한 부분은 원문 검토 경로로 보냅니다.

레코드는 순서대로 읽습니다. 다만 **가장 큰 개별 레코드는 메모리에 들어가야 합니다.** 업로드 크기 상한을 없앤 것이 무제한 메모리나 그래프 한 개의 무제한 객체 수를 뜻하지는 않습니다. 큰 파일의 결과는 부분 그래프로 나뉩니다.

## 3. Jev 선택 판정과 Codex 대체

Jev는 표의 본문·설명 열에 반복되는 서술 분류·복잡도 확인·관계 유형 후보 판정을 수행합니다. `sourceMappings[].semanticColumns`로 선언한 의미 분석 대상이 있으며 API 키가 설정되어 있으면 이 보조 판정을 사용할 수 있습니다. `textStrategy: "codex"` 또는 빈 `jevEligibleLinkTypes`는 보조 분류를 막지 않습니다. 자료별 질문은 `processing.decisionRules`로 설계하며, 이전 정의에 질문이 없으면 서버의 기본 질문을 사용합니다.

| 상황 | 새 온톨로지 기반 분석 |
| --- | --- |
| Jev 키 없음 또는 의미 분석 대상 없음 | 자료에 맞는 코드 변환·Codex 분석을 사용하고 미사용 사유 표시 |
| 의미 분석 열에 적합한 선택형 질문 | Jev 보조 분류 후 원문을 Codex로 분석 |
| 독립적인 짧은 기록으로 분류 | 원문 최대 4개·합계 최대 6,000자를 묶어 Codex로 분석 |
| 복잡·재인용·반박·핵심 경로 판정 불확실·분류 오류 | 원문을 개별 Codex 분석에 배정 |
| 별도 직접 추출 정책과 단순 관계의 입력 조건 충족 | Jev로 직접 추출 후 스키마·원문 검증 |
| Codex 분석이나 검증 실패 | 해당 구간을 저장하지 않고 실패·재개 상태로 보관 |

모델이 반환하는 확률은 수용 기준이며 실제 정확도를 보장하는 값이 아닙니다. 새 분석에서는 `CLUEVIA_JEV_FALLBACK=false`를 설정해도 불확실한 Jev 부분 결과를 완료본으로 저장하지 않습니다. 해당 변수는 **이전 처리 방식으로 시작한 작업**의 호환 설정입니다. 이전 작업은 재개할 때 기존 설정과 처리 경로를 유지할 수 있습니다.

자료의 형식 파싱·식별 키 연결·캐시 조회는 코드가 담당하고, Jev는 입력된 근거에 대해 허용된 선택지를 판단합니다. 보조 판정은 사실이나 식별 키를 생성하지 않으며, 관계 후보가 없다는 답변 때문에 원문을 제외하지 않습니다. Codex에는 각 기록의 원문과 출처 ID를 유지하여 전달합니다. 묶음 분석 여부는 서술 태도와 독립 처리 가능성의 확신도·원문의 문맥 단서로 정합니다. 관계 후보나 추가 분류만 불확실한 경우에는 불확실성을 유지한 채 Codex가 원문을 확인합니다.

이와 별도로 `textStrategy: "jev-assisted"`와 `jevEligibleLinkTypes`가 선언된 단순 관계는 Jev의 직접 추출을 사용할 수 있습니다. 명시적으로 인용된 두 이름과 단일 관계가 있는 짧은 문장에서 전체 내용의 표현 가능 여부·양쪽 객체 유형·관계 방향을 판정합니다. 부정·시간·수치·상충하는 주장 등은 Codex로 넘깁니다. 반복 판정은 Codex가 선언한 JSON 정책과 고정 실행기를 사용합니다. 자세한 계약은 [Jev 반복 판정](jev-decision-plan.md)을 참고하세요.

## 시간 초과와 재개

새 분석의 일반 문서 구간은 최대 8,000자입니다. Codex 응답이 시간 초과되면 저장하지 못한 해당 구간만 겹치는 문맥을 포함해 둘로 나누고 재시도합니다. 구간당 분할은 최대 두 단계이며 작은 구간까지 계속 실패하면 실패 상태와 재개 위치를 보관합니다. 이미 저장한 그래프는 재생성하지 않습니다. 분할된 계획과 전체 구간 수는 함께 저장되어 재시작 후에도 이어집니다.

기존 구조화 자료 작업이 추출 시간 초과로 실패했고 아직 완료한 구간과 그래프가 없다면, **남은 구간 이어서 분석**에서 직접 변환 매핑을 한 번 다시 설계합니다. 기존 정의는 이력으로 남깁니다. 서버 코드를 변경한 뒤에는 개발 서버를 재시작해야 새 처리 경로가 적용됩니다. 타임아웃 값을 늘리는 것만으로 대량 행을 모델이 다시 작성하도록 두지 않습니다.

겹치는 문맥은 구간 경계의 누락을 줄이지만 문서 전체에 걸친 모든 관계를 해결하는 보장은 아닙니다. 모델 분류 확률과 인용 검증만으로 사실성·정확도를 보장하지 않습니다.

## 속도와 캐시

1. Codex가 한 작업의 스키마를 설계하면 검증된 표 레코드 매핑은 코드로 수행합니다.
2. 본문·설명 열은 Jev의 선택형 분류를 활용하고, 독립적인 짧은 기록은 묶어서 Codex로 분석합니다. 복잡하거나 불확실한 기록은 개별로 처리합니다. 분류 자체가 원문 분석을 생략하지 않으므로 전체 속도 개선 폭은 자료마다 다릅니다.
3. Jev 동시 요청은 `TYPESAFE_CONCURRENCY`로 제한합니다. 기본 4, 허용 1–16이며 제공자 속도 제한에 따라 재시도가 발생할 수 있습니다.
4. 추출 캐시는 원문과 처리 설정뿐 아니라 **온톨로지 정의**도 구분합니다. 스키마가 다른 분석의 결과를 그대로 재사용하지 않습니다.
5. 실패·취소·재시작 후 완료한 구간은 다시 호출하지 않고 미완료 구간부터 이어갑니다.

같은 파일이라도 새 질문으로 다른 온톨로지를 설계하면 설계 호출과 추출 호출이 다시 필요할 수 있습니다. 비용과 소요 시간은 자료 형식, 검증된 매핑 비율, Codex로 넘어가는 구간, 모델·네트워크에 따라 달라집니다.

### 이전 경로의 측정 기록

2026-10-10에 이전 고정 스키마 처리 경로로 합성 CSV 3,173,814바이트·16,000행을 업로드·변환·검증·저장까지 9.516초에 처리했습니다. 184개 그래프에 모든 행을 보관했고 당시 모델 호출은 0회였습니다. WSL 임시 로컬 디스크에서 측정한 결과이며 **현재 Codex 설계 단계가 포함된 전체 실행 시간은 아닙니다.**

같은 날 명시적 한 문장 관계로 실제 Jev 호출 2회·HTTP 200, 객체 2개·관계 1개 저장을 확인했습니다. 단일 예제의 연결 검증이며 새 도메인이나 큰 문서의 정확도·속도 기준으로 사용하지 않습니다.

### 새 경로의 실제 연결 확인

2026-10-10에 합성 고객·주문 CSV로 실제 Codex 설계 호출과 SQLite 저장을 확인했습니다. Customer·Order 유형, boolean·decimal 속성, 관계·컬럼 매핑을 설계한 뒤 고객 2개·주문 3개·관계 3개를 저장했습니다. Codex 설계 1회, Jev 0회, 행별 모델 호출 0회였습니다. 별도 메모리 DB에서 수행한 기능 검증이며 실제 업무 데이터의 정확도나 대용량 속도를 보장하는 측정은 아닙니다.

같은 날 실제 시간 초과 작업의 CSV·JSONL 5개 자료를 읽기 전용으로 검증했습니다. Codex 설계 1회에 105.938초, 이후 1,147행의 직접 변환 및 처리 계획 준비에 1.151초가 걸렸습니다. 정형 데이터 15구간, 별도 의미 분석 40구간으로 나뉘었고, 매핑 실패로 모델에 넘기는 표 구간은 0개였습니다. 의미 분석 40구간의 모델 실행과 최종 그래프 저장은 이 측정에 포함하지 않았습니다. 기존 작업은 변경하지 않았으며 별도 메모리 저장소에서 확인한 결과입니다.

| 개별 분석 배정 | 복잡성·불확실성·분류 오류 등으로 개별 분석에 배정한 구간 수 |
| Codex 설계·분석 | 실제 Codex 실행 수. 설계·추출·수정 재호출 포함 |
| Codex 묶음 분석 | 여러 짧은 기록을 한 번에 전달한 Codex 실행 수 |
| 기존 분석 재사용 | 추출 캐시를 사용한 구간 수 |
| 추가 검토 대상 | 추가 검토가 필요했던 구간 수. Codex로 대체한 구간 포함 |

**Jev 처리**에는 서버가 선택한 경로와 0회일 때의 미사용 사유를 표시합니다. **Jev 판정 내역**을 펼치면 자료별 경로·선택 결과·확신도를 확인할 수 있으며 필요할 때 새로고침합니다. 한 API 요청에 여러 질문을 전달할 수 있으므로 호출 수와 판정 건수는 다릅니다. 처리 수치는 청구 금액이나 예상 완료 시간이 아닙니다. 저장된 온톨로지 링크에서 구조를 확인하고, 부분 그래프의 이전·다음 버튼으로 각 구간 결과를 열 수 있습니다. 전체 구간 처리와 모든 사실의 빠짐없는 추출은 같지 않으므로 근거를 함께 검토하세요.

## 저장과 범위

원본, 버전이 있는 온톨로지, 그래프, 객체·관계의 근거, 재개 위치, 추출 캐시는 서버 데이터 디렉터리에 보관합니다. 온톨로지·유형·기본 키를 기준으로 객체를 연결하고 서로 다른 온톨로지는 분리합니다. 이름처럼 출처 범위로만 식별할 수 있는 키는 `identityScope=source`로 저장해 다른 원본 자료와 자동 병합하지 않습니다. 자료 전체에서 유일한 ID는 `identityScope=ontology`를 사용할 수 있습니다.

업로드 기본 제한은 `CLUEVIA_MAX_UPLOAD_MB=0`이며 저장 공간·프록시 제한은 별도로 적용됩니다. PDF·이미지·Office·압축 파일은 먼저 UTF-8 텍스트를 추출해야 합니다. 완성 그래프 JSON 가져오기의 크기 제한은 원본 업로드와 별개입니다.

온톨로지 설계에 필요한 자료와 문서 구간은 연결된 Codex 또는 TypeSafe 서비스로 전송됩니다. 표의 전체 행은 검증된 매핑으로 서버에서 변환합니다. 정확한 인용 검증은 원문에 인용이 존재하는지 확인하며 관계 해석의 사실성까지 증명하지는 않습니다.

## 간결한 설계도와 온톨로지 빌더

설계 단계에서 Codex는 `ontologyBlueprintSchema`에 맞는 간결한 설계도를 반환합니다. 서버의 `buildOntologyDefinition`이 상태·표시 메타데이터·기본값을 채우고 기존 온톨로지 검증기를 실행합니다. 같은 이름의 컬럼 매핑은 문자열 목록으로 작성할 수 있습니다. 공유 속성·인터페이스·Value Type 등은 필요할 때 `extensions`에 선언합니다.

모델이 매번 반복하는 JSON 작성량을 줄이는 방식입니다. 실제 소요 시간은 자료·모델 응답과 재검증 여부에 따라 달라지며 고정된 속도 배수를 보장하지 않습니다. 모델에 셸이나 외부 도구 실행 권한을 추가하지 않습니다. 빌더는 서버에서 자동 호출합니다.

로컬에서 모델·API 키 없이 사용하려면:

```powershell
python scripts/build_ontology.py --template commerce | Set-Content -Encoding utf8 blueprint.json
python scripts/build_ontology.py blueprint.json | Set-Content -Encoding utf8 ontology.json
```

템플릿 파일을 수정해 원하는 객체·속성·관계를 정의할 수 있습니다. 두 번째 명령은 잘못된 참조나 키·타입 계약을 검증한 뒤 완성된 정의 JSON을 출력합니다. 정의 생성만 수행하며 실제 객체나 그래프를 저장하지 않습니다.

## 출처 ID와 실제 식별자의 구분

속성의 `valueSource`는 값의 출처를 명시합니다.

| 값 | 처리 |
| --- | --- |
| `evidence` | 원문에서 추출하는 값. 실제 문서 번호·IMO·주문 번호 등 식별 키는 인용문과 대조 |
| `documentId` | 서버가 전달한 출처 문서의 ID |
| `documentName` | 서버가 전달한 출처 문서의 이름 |
| `evidenceId` | 객체 유형·출처 범위·정확한 인용문으로 서버가 만드는 추출 기록 ID |

서버가 만드는 속성은 모델 출력에서 생략합니다. 출처 메타데이터를 실제 업무 식별자로 대신 사용하지 않습니다. 예를 들어 보고서 원본에 `doc_id` 컬럼이 있으면 해당 값은 `evidence`이며, 임시 `source-1` 값으로 대체할 수 없습니다. 캐시를 재사용할 때도 출처를 원본 자료에 맞춰 재연결합니다.

기존 분석이 Primary Key 인용 오류로 실패했고 아직 완료한 구간·저장된 그래프가 없다면, **남은 구간 이어서 분석** 시 온톨로지를 다시 설계합니다. 원본 자료와 이전 정의는 보존하고 새 버전을 사용합니다. 이미 저장된 그래프가 사용하는 정의는 자동 변경하지 않습니다.
